# Goldfish: понятность и самодостаточность

Дата: 26.10.2026. Прочитаны только Markdown/YAML-файлы пакета. История проектирования, внешние источники и реализация не проверялись. Ни код приложения, ни работающая система не исследовались.

## Восстановленный замысел

Нужен новый телефонный справочник на Python для двух равноправных пользователей в локальной сети: общий набор до 100000 контактов, несколько RU-телефонов на контакт, точный поиск в обе стороны, CRUD через русский браузерный UI и API. Тезки и общие телефоны допустимы; UUID задает идентичность. Версии защищают от перезаписывания чужих правок. CSV добавляет или пропускает контакты, предварительно проверяется и применяется атомарно. Данные должны переживать обычный сбой; полная потеря сервера покрывается внешними копиями и проверяемым восстановлением. Сейчас поставляется только спецификация.

Пакет позволяет восстановить продукт без переписки. Есть порядок чтения, приоритет документов, связь требований с CUJ и планом приемки. Отдельно обозначены пользовательские требования, решения автора и еще не измеренные цели. CUJ покрывают главные бизнес-пути, актуализацию, перенос и восстановление. Полный исходный текст задания и подтверждения пользователя не включены: происхождение U-01…08 представлено пересказом, поэтому независимая проверка точности согласования невозможна, но для понимания продукта переписка не нужна.

## Значимые замечания

### GF-01 · P1 · Максимальный справочник нельзя гарантированно перенести собственным CSV

Места: `docs/csv.md` (50 MiB), `docs/acceptance.md` (100000 контактов × 10 телефонов), DX-05 «Круговой перенос», CUJ-05.

Экспорт не ограничен размером и обязан содержать весь справочник, а импорт ограничен 52428800 байтами. Даже минимальная строка с UUID (36), двумя запятыми (2), именем из одного ASCII-символа (1), экспортированным телефоном с апострофом (13) и CRLF (2) занимает 54 байта. Миллион строк — уже 54000000 байт без заголовка/BOM. При реальных именах файл существенно больше. Таким образом, разрешенная модель данных противоречит обещанному обратимому переносу в пустой экземпляр.

Нужно согласовать лимит импортируемого файла с максимальным экспортом или явно определить другой гарантированный протокол полного переноса. Добавить приемку экспорт → импорт максимального набора с длинными многобайтными именами. Это блокирует приемку обещания полного CSV-переноса, хотя не мешает начать несвязанные части реализации.

### GF-02 · P2 · Потерянный ответ upload не покрыт восстановлением импорта

Места: `docs/ui.md` («при неопределенном ответе проверяется import_id»), `docs/api.md` (`POST /imports` генерирует import_id только в ответе), CUJ-05.

При потере ответа первого POST клиент еще не знает import_id и не может выполнить указанное действие. Контракт не содержит клиентского идентификатора загрузки, списка своих импортов или явного правила безопасной повторной загрузки. Для commit восстановление описано достаточно, для upload — нет.

Определить ветку потери ответа проверки файла: например, повторная загрузка с новым батчем допустима, старый истекает и без подтверждения не применяется; либо добавить идентификатор повтора. Отразить действие пользователя и приемочный сценарий.

### GF-03 · P2 · В документах разная точка начала RTO

Места: RS-04 «Потеря сервера» и `docs/acceptance.md`, DR-01 п. 4.

Сценарий RS-04 отсчитывает час после начала восстановления оператором; DR-01 — после обнаружения и регистрации инцидента. Ожидание оператора между этими моментами меняет итог приемки. Следует закрепить одну точку начала и одинаково выразить ее в требовании, CUJ-06 и DR-01. Зависимость от готового резервного сервера и доступного оператора уже раскрыта достаточно.

## Вердикт

Замысел понятен, основные решения и CUJ самодостаточны. Есть один блокер полного выполнения заявленного CSV-переноса (GF-01) и два ограниченных пробела контракта/приемки. После согласования этих пунктов разработчик сможет реализовывать документ без домысливания указанных веток. Этот вывод относится только к спецификации и не подтверждает работоспособность будущей реализации.

# Телефонный справочник: спецификация для разработки

Версия 1.0 · 26 октября 2026 · Язык документации: русский.
Это самостоятельный проект

## Что строим
Браузерный телефонный справочник на Python для двух пользователей в локальной сети. Есть общий набор контактов, точный поиск имени по телефону и телефонов по имени, добавление, изменение, удаление и CSV-обмен. Целевая емкость — 100 000 контактов. Даты в интерфейсе — МСК.

«С нуля» означает новое приложение с собственной предметной логикой и интерфейсом. Готовые СУБД и библиотеки разрешены; собственный движок хранения не разрабатывается. Основание — согласованный выбор телефонного справочника вместо движка БД. Django/PostgreSQL и детали контрактов ниже — проектные решения автора, а не дословные требования заказчика.

## Где применены принципы задания
| Принцип | Конкретный результат |
|---|---|
| Critical User Journey | CUJ-01…06 с исходными условиями, шагами, результатом и отказами |
| Elephant + Goldfish | Согласование контекста в основном диалоге; независимая проверка только файлов без истории переписки |
| Architectural Decision Record | ADR-001…004: контекст, выбор, альтернативы, последствия, основания пересмотра |
| LLM-expert review | Проверка понятности и экспертная проверка архитектуры/контрактов; замечания с привязкой к документам |
| Fact Grounding | Разделение требований пользователя, внешних фактов, проектных решений и непроверенных целей; ссылки на первоисточники |

## Как использовать OpenSpec
Пакет соответствует схеме `spec-driven`: proposal → specs/design → tasks. Новые возможности описаны как `ADDED Requirements`, каждое требование использует SHALL и имеет сценарии WHEN/THEN. Текущие спецификации не объявлены реализованными: `openspec/specs/` намеренно пуст до реализации и архивирования изменения.

В окружении с установленным OpenSpec из корня этого пакета следует выполнить `openspec validate create-phonebook --strict`. CLI-проверка и ее фактический статус указаны в отчете проверки. Не запускать apply в рамках данного задания: требуется только спецификация. Все задачи реализации остаются незавершенными.

Требования в spec.md имеют приоритет над дизайном; API и CSV — нормативные детализации, на которые ссылаются требования. ADR объясняют решения. При противоречии документы исправляют до реализации, а не выбирают удобную трактовку. Новое поведение оформляют отдельным изменением OpenSpec.

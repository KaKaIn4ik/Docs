# Design: телефонный справочник

## Context
Новый проект без исходного кода. Функциональная область — proposal.md; нормативное поведение — specs и docs/api.md, docs/csv.md. Пользователь согласовал библиотечное приложение вместо самописного движка, локальную сеть, RU-номера, 100 000 контактов и двух пользователей. Все последующие имена компонентов — план реализации, а не утверждение о существующем коде.

## Goals / Non-Goals
Цель — простая реализация с одной предметной логикой для UI и API, предсказуемыми транзакциями и проверяемым восстановлением. Не строим микросервисы, отдельный JavaScript SPA, поисковый кластер, очередь задач, собственную криптографию и собственную СУБД.

## Decisions
- ADR-001: Python 3.12, Django 5.2 LTS, PostgreSQL 18, серверные шаблоны; версии указаны как базовая линия проекта, patch-релизы фиксируются и проверяются при начале разработки.
- ADR-002: независимый UUID контакта, таблица телефонов, нормализованные ключи, версия для конкурентного доступа.
- ADR-003: двухэтапный CSV, неизменяемый файл, добавление/пропуск по UUID, атомарный commit.
- ADR-004: устойчивый коммит, внешние копии и тест восстановления; МСК только для отображения.

## Компоненты и поток данных
Браузер или API-клиент → HTTPS reverse proxy → один Django-сервис → PostgreSQL. UI использует серверные формы и шаблоны; HTTP API использует JSON-представления. Оба вызывают общие сервисы контактов, поиска и импорта. Оператор обслуживает учетные записи и копии. Доступ к PostgreSQL — только с сервера приложения/хоста резервирования, не из пользовательской сети. Два пользовательских аккаунта не имеют прямых учетных данных БД.

Импорт синхронный: upload/validate и commit — разные HTTP-запросы. Минимум два web worker; таймаут тяжелых операций 180 секунд. Цель импорта/экспорта на максимальном объеме — ≤120 секунд, проверяется отдельно, не входит в p95 интерактивного поиска. Redis/Celery не нужны на старте; если проверка длительности не проходит, архитектуру пересматривают ADR, а не скрыто обрывают запросы.

## Логическая модель данных
| Сущность | Поля и ограничения |
|---|---|
| Contact | id UUID PK; name varchar(200); name_key text NOT NULL; version bigint ≥1; created_at/updated_at timestamptz NOT NULL |
| ContactPhone | contact_id FK ON DELETE CASCADE; phone varchar(12); UNIQUE(contact_id, phone); канонический RU номер |
| DirectoryState | одна строка: id=1, contact_count 0…100000; блокировка сериализует все мутации контактов |
| ImportBatch | id UUID PK; owner FK; state validated/committed/expired; sha256; temporary_path; expires_at; created_count; skipped_count; committed_at |
| User / Session | штатные таблицы Django; только две пользовательские учетные записи, административный доступ — эксплуатационный |

Никакой глобальной уникальности имени или телефона. Индексы Contact(name_key, id), ContactPhone(phone, contact_id), первичные ключи и уникальность пары contact/phone. Нормализованный ключ вычисляется приложением, сравнивается побайтно/детерминированно, не через locale-зависимый ILIKE. Проверка 1–10 телефонов и принадлежности RU выполняется сервисом внутри транзакции; прямые записи в БД запрещены эксплуатационным контрактом. Контроль целостности сверяет contact_count и фактическое количество при диагностике и после restore.

## Транзакции и конкурентность
Все операции создания, PUT, DELETE и commit импорта получают SELECT FOR UPDATE строки DirectoryState, затем при необходимости контакт/ImportBatch. Единый порядок блокировок предотвращает взаимные блокировки. Для двух пользователей это сознательная простота ценой последовательных записей. Чтения не берут эту блокировку и используют MVCC. Для count + страницы и экспорта — одна read-only транзакция REPEATABLE READ.

Создание проверяет UUID и емкость после блокировки. PUT/DELETE сверяют текущую version под блокировкой, затем меняют весь агрегат. Счетчик меняется в той же транзакции только при создании/удалении. Commit импорта под той же блокировкой перечитывает батч, актуальные UUID и емкость; фиксирует контакты и state=committed вместе. Повтор видит сохраненный итог. Файлы после commit удаляются вне транзакции, периодическая очистка повторяет удаление при сбое. Очистка validated-батча получает DirectoryState, затем ImportBatch; только после проверки срока и фиксации expired удаляет файл. Работающий commit защищен теми же блокировками. Срок проверяется после получения блокировки до применения; начатый вовремя commit может закончиться после срока. Незавершенная транзакция откатывается PostgreSQL; неподтвержденный батч остается validated и может быть применен до истечения срока.

Все строки CSV валидируются до записи контактов с потоковым чтением и ограничением байтов/строк; группировка до 100000 UUID может храниться в памяти, при максимальном файле проверяется расход памяти ≤2 GiB на worker. Для commit данные читаются из сохраненного файла, повторно проверяется его хеш. Общая блокировка на время commit может задерживать другие записи; это ограничение документируется и проверяется в приемке.

## Защита и эксплуатация
Django auth, серверные сессии, CSRF, экранирование HTML; ORM/параметризованные запросы. HTTPS с доверенным в локальной сети сертификатом. DEBUG выключен, разрешенные hostnames заданы, DB/backup учетные данные вне репозитория. Ограничение входа реализуется отдельно (штатная auth-система не обещает throttle); счетчики на стороне сервера, переживают перезапуск worker. IP определяется только по доверенному proxy.

Логи прокси не включают query string; логи приложения — только разрешенные метаданные. База и резервные копии — на зашифрованных носителях/в зашифрованном хранилище; ключ восстановления хранится отдельно от сервера. Нет публичного доступа и внешней аналитики.

## Risks / Trade-offs
- Одна машина → возможен простой; отказоустойчивый кластер не обещается.
- Последовательные записи → длинный импорт задерживает сохранения; ограничение 120 секунд и отдельная приемка конкурентного чтения/записи.
- Метаданные номеров меняются → версия фиксируется, обновление требует проверки фикстур и ADR при изменении правил.
- Имена и номера не определяют человека → внешний CSV обязан содержать UUID, автоматическое слияние запрещено.
- CSV из редактора может преобразовать номера → текстовый столбец и документированное обратимое экранирование.
- Копии не выполнялись/повреждены → RPO не обеспечивается; уведомление оператору и испытание restore обязательны.

## Migration Plan
Проект новый: миграции создают таблицы и ограничения; оператор создает две учетные записи. На пустой БД выполняются приемочные проверки и DR-репетиция на синтетических данных. Затем первая резервная копия и допуск пользователей. Перед каждым будущим обновлением схемы — внешняя проверенная копия, режим обслуживания и согласованный путь отката. При неуспешной миграции пользователи не допускаются; восстанавливаются предыдущие приложение/схема/копия. Импортные временные файлы и сессии при аварийном восстановлении не восстанавливаются.

| contacts/normalization.py | чистые правила имени/номера |
| contacts/services.py, contacts/selectors.py | транзакционные изменения и чтение |

| exchange/csv_format.py, exchange/services.py, exchange/api.py | формат, проверка и commit |
| accounts/views.py, accounts/throttling.py | вход/выход и ограничения попыток |

Это карта для разработчика: перечисленные файлы пока не создаются. Сигнатуры внутренних функций не фиксируются, потому что контрактом служат наблюдаемое поведение и API; конкретные внутренние имена допустимо уточнять без изменения поведения.

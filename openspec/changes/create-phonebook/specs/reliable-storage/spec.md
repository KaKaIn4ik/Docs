# Spec Delta

## Purpose
Проверяемые гарантии сохранности и работы общего справочника заданной емкости с процедурой восстановления.

## ADDED Requirements

### Requirement: RS-01 Подтвержденная запись
Система SHALL сообщать об успешной записи только после устойчивого коммита. Сбой процесса приложения, ОС или СУБД при сохранном исправном диске не теряет подтвержденные изменения; незавершенные операции не оставляют частичных данных.

#### Scenario: Перезапуск
- **WHEN** после успешного ответа аварийно остановлены приложение и СУБД, затем запущены снова
- **THEN** контакт присутствует целиком с подтвержденной версией.

#### Scenario: Сбой до коммита
- **WHEN** авария произошла до завершения изменения
- **THEN** после запуска нет частичного состояния; клиент проверяет фактический результат чтением.

### Requirement: RS-02 Емкость
Система SHALL поддерживать 100 000 контактов с максимум 10 телефонами каждый. Создание сверх 100 000 отклоняется с 409 capacity_exceeded; чтение, изменение и удаление существующих контактов доступны.

#### Scenario: Граница
- **WHEN** в справочнике 99 999 контактов, одновременно создают два новых
- **THEN** успешно создан ровно один; итог 100 000.

#### Scenario: Большой импорт
- **WHEN** импорт новых UUID превысил бы емкость
- **THEN** весь импорт отклонен; пропускаемые совпадающие UUID не увеличивают счетчик.

### Requirement: RS-03 Скорость поиска
Система SHALL обеспечивать p95 ≤500 мс для точного поиска на 100 000 контактах при двух одновременных пользователях в условиях docs/acceptance.md. Это критерий приемки, а не утверждение об уже измеренной скорости.

#### Scenario: Нагрузочная приемка
- **WHEN** выполнен профиль PERF-01 на эталонном стенде
- **THEN** p95 каждого поискового направления ≤500 мс, доля ошибок 0%, результаты корректны.

### Requirement: RS-04 Резервные копии
Система SHALL создавать копии каждые 12 часов, хранить их вне сервера не менее 7 суток и контролировать успешность. При потере сервера целевые RPO ≤24 часов и RTO ≤1 часа проверяются восстановлением по регламенту.

#### Scenario: Потеря сервера
- **WHEN** обнаружена и зарегистрирована потеря сервера и начато восстановление по DR-01
- **THEN** за ≤1 час с момента обнаружения и регистрации инцидента восстановлены все данные снимка; его возраст на момент инцидента ≤24 часов.

#### Scenario: Сбой копирования
- **WHEN** очередная копия не создана или не прошла проверку
- **THEN** оператор получает уведомление в течение 15 минут; статус копии не помечен успешным.

### Requirement: RS-05 Время
Система SHALL хранить временные отметки как абсолютные моменты UTC, отдавать в API RFC3339 с Z и отображать в UI/эксплуатационных отчетах в Europe/Moscow с явным обозначением МСК. Часовой пояс клиента не меняет отображение.

#### Scenario: Часовой пояс
- **WHEN** клиент с любым часовым поясом открывает событие 2026-10-26T09:00:00Z
- **THEN** UI отображает 26.10.2026 12:00:00 МСК; API сохраняет исходный момент.

### Requirement: RS-06 Защита диагностических данных
Система SHALL исключать имена, телефоны, CSV-содержимое, пароли, сессии и поисковые ключи из журналов. Допустимы request_id, операция, статус, длительность и служебный UUID. Копии доступны только оператору.

#### Scenario: Журналирование поиска
- **WHEN** выполнен поиск имени и экспорт
- **THEN** в журналах приложения и прокси отсутствуют параметры поиска и содержимое ответа; есть статус и длительность.
